# 证据与调研规范

## 一、仓库取证顺序

按“低成本全景 → 高价值链路 → 历史证据”推进：

1. `AGENTS.md`、README、构建文件和目录树；
2. 配置文件、数据库迁移、实体、枚举和接口定义；
3. Controller/Service/Domain/Repository/Mapper；
4. 定时任务、消息处理、缓存、外部客户端和异常处理；
5. 单测、集成测试、压测或故障演练；
6. Git 提交、blame 和关键设计的演进。

优先用 `rg --files` 和 `rg` 搜索，不对整个仓库进行无目标通读。不要使用固定关键词表：先从构建清单、框架、配置键、核心类型和业务术语生成项目专属搜索词，再围绕异常处理、状态变化、外部副作用、资源边界和测试证据扩展。

## 二、事实登记表

写正文前建立内部底稿：

| 编号 | 结论 | 标签 | 证据位置 | 可否写入简历 | 备注 |
|---|---|---|---|---|---|
| F-01 | 示例：状态更新带旧状态条件 | F | Mapper/测试/Git | 可以概括 | 不复制源码 |
| R-01 | 示例：该条件用于避免重复推进 | R | F-01 + 调用链 | 可以谨慎表达 | 标明推导 |
| P-01 | 示例：规模扩大后引入 MQ | P | 架构分析 | 不可写成现状 | 放演进 |
| U-01 | 示例：生产峰值 QPS | U | 待本人确认 | 不可以 | 不猜数值 |

文档中不必处处显示标签，但强结论、演进方案和待确认事实必须让读者能区分。

## 三、个人贡献取证

### 1. 先确定 Git 口径

当任务涉及个人贡献、团队分工或提交统计时，先从用户要求和仓库现场确定四项口径：

| 维度 | 可选范围 | 何时需要询问 |
|---|---|---|
| 人员 | 指定作者 / 全部贡献者 / 指定作者为主、团队为背景 | 用户只说“看 Git”但没有说明归属目标时 |
| 引用 | 当前分支 / 指定分支 / `--all` 全部可见引用 | 多分支、发布分支或平行历史可能影响结论时 |
| 时间 | 全部历史 / 指定起止日期 | 用户只关心某段实习、迭代或版本时 |
| 身份 | 中文名、英文名、邮箱和历史别名 | 同一人可能存在多个提交身份时 |

将口径记入事实底稿，例如：“作者范围：王某及已确认邮箱；引用范围：origin/master；时间：2026-05-01 至 2026-08-31；merge 不计为独立功能”。用户要求分析全部贡献者时，先生成作者分布和模块分工，再决定是否逐人深挖；不得把团队总代码量写成某个人的成果。

### 2. 确认身份

```bash
git shortlog -sne --all
git log --all --format='%an <%ae>' | sort -u
```

姓名可能存在中文、拼音、公司邮箱等多种形式。只有能可靠归并时才合并统计。

### 3. 查看贡献范围

```bash
git log --all --author='<姓名或邮箱>' --date=short \
  --pretty=format:'%h%x09%ad%x09%s'

git log --all --author='<姓名或邮箱>' --numstat \
  --format='commit %H'

git show --stat <commit>
git show --format=fuller <commit> -- <关键路径>
```

命令中的 `--all` 应按已确认的引用范围替换为当前分支、指定引用或全部引用；需要限定时间时加入 `--since` 和 `--until`。先按提交主题和文件职责聚类，再阅读最关键的 diff。统计行数只能帮助发现重点，不能直接代表贡献价值。

多个分支可能包含同一补丁的 merge、cherry-pick 或重放提交。计数前比较提交可达性、主题、文件和 patch-id；无法可靠去重时报告“可见提交对象数”和采用的口径，不包装成独立功能数。

### 4. Git 能证明与不能证明的内容

Git 通常能证明：

- 编写或修改了哪些代码、测试和配置；
- 某个机制在何时引入或修正；
- 对哪些模块进行了持续维护；
- 是否参与评审后的修订。

Git 单独不能证明：

- 需求和架构一定由该作者独立提出；
- 功能已经生产上线且长期稳定；
- 性能提升百分比、QPS、故障率或业务收益；
- 团队决策过程和跨团队推动范围。

可以把零散工作重组为更高层的面试故事，但每个动词必须守住边界：

- 有直接实现证据：使用“设计并实现”“重构”“补齐”；
- 主要参与实现：使用“参与设计并负责……实现”；
- 只有维护或修复证据：使用“负责维护并优化”；
- 团队成果：使用“项目采用……，我主要负责……”。

## 四、技术主题发现与取证

### 1. 从代码生成候选主题

依次观察：

- 构建依赖、框架插件和基础设施客户端；
- 核心对象、状态变化、唯一性和数据生命周期；
- 跨进程、跨服务、跨线程或跨事务边界；
- 外部调用、异步任务、回调、重试和补偿；
- 计算、存储、网络、模型调用等昂贵资源；
- 鉴权、数据隔离、敏感信息和输入输出边界；
- 测试、指标、日志、Trace、发布与故障处理；
- Git 中反复修改、修复或重构的热点。

依赖声明只能证明“可能使用”。必须继续找到配置、调用链、数据落点和测试，才能确认实际用途。表名、类名或多数据源等表面特征也不能单独证明某种架构能力。

### 2. 从约束生成深挖问题

对每条关键链路追问：

- 哪个不变量最容易被破坏；
- 哪一步可能重复、乱序、超时、部分成功或资源耗尽；
- 哪个设计决定了性能、正确性、安全性、成本或可维护性；
- 当前方案在哪个规模或需求变化下失效；
- 测试和观测能否证明它按预期工作。

再根据具体项目选择原子性、幂等、缓存、消息、运行时、协议、前端、AI 评测、安全、工程化等相应知识，不反过来用知识清单套项目。

### 3. 形成主题筛选表

| 候选主题 | 代码证据 | 项目核心度 | 个人参与 | 当期面试信号 | 可深挖性 | 决策 |
|---|---|---|---|---|---|---|
| 示例：工具调用状态管理 | 类/配置/测试 | 高 | 高 | Agent 岗常见 | 高 | 深写 |
| 示例：通用缓存八股 | 无调用证据 | 低 | 无 | 后端常见 | 中 | 删除或仅作反事实 |

不要求机械打分，但必须能解释为什么选、为什么不选。

## 五、外部面经调研

### 查询设计

先提取四组词，再组合查询：

1. 目标岗位与阶段：如校招、社招、后端、全栈、Agent 工程；
2. 项目类型：如工作流、交易、内容平台、RAG 应用；
3. 代码候选主题：来自依赖、核心链路和实现难点；
4. 追问意图：项目深挖、设计取舍、故障场景、性能、基础原理、系统设计。

不同查询应覆盖不同意图，不能用同一句重复搜索凑次数。发现新高频主题后进行第二轮定向调研，并用官方资料校准答案。

### 记录格式

| 平台 | 日期 | 查询词 | 样本类型 | 可迁移追问 | 可信度备注 |
|---|---|---|---|---|---|
| 小红书 | YYYY-MM-DD | …… | 一手面经/总结 | …… | 是否有完整上下文 |

“出现较多”只能作为定性观察；没有系统抽样方法时，不写精确占比。

### 来源优先级

1. 一手面试复盘；
2. 与入选主题直接相关的官方文档、标准或论文；
3. 大厂公开技术文章；
4. 高质量社区总结；
5. 聚合转载，仅用于发现关键词。

面经决定“面试官可能怎样问”，官方资料决定“机制怎样准确回答”，项目仓库决定“本项目实际怎样做”。

## 六、保密和干净示例

不得写入：

- 密码、Token、AK/SK、Cookie、手机号、身份证、订单明细；
- 内网域名、IP、数据库连接串、真实 Topic 密钥；
- 可还原公司完整业务实现的大段源码；
- 未公开的生产规模、事故细节和商业数据。

允许保留：

- 经用户要求且仓库可验证的系统名、表名、类名和状态名；
- 经重写的最小示意代码；
- 不含敏感值的架构关系；
- 个人提交的事实范围。

示意代码必须重新组织变量、删除业务数据，并在代码块前标注用途和非源码性质。
