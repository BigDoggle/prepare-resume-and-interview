# 自适应项目面试文档蓝图

## 使用方式

首次生成或全量重构时完整读取本文件。先完成仓库取证、面试调研和主题筛选，再设计文档；不要反过来用文件模板决定分析内容。

## 一、先确定信息架构

把候选内容聚成若干“主题簇”。一个主题簇应同时满足：

- 能回答一个清晰的面试问题；
- 在仓库中存在足够证据；
- 与项目核心链路或个人贡献有关；
- 能讲出约束、方案、取舍、边界和验证；
- 与其他主题簇没有大面积重复。

根据篇幅决定合并或拆分。单个主题不足以形成完整论证时并入相邻文档；一个文档出现多个互不相关的深挖中心时再拆分。文件名使用该项目真实主题，不为保持编号完整而建空文档。

## 二、稳定入口

### 人类阅读入口

通常使用 `README.md`，承担：

- 项目一句话定义和资料适用范围；
- 动态生成的文档地图；
- 按用户时间设计的阅读路线；
- `F/R/P/U` 事实边界；
- 保密说明、更新时间和待确认事项。

入口只做导航，不重复技术正文。

### Agent 阅读入口

通常使用 `AGENT-CONTEXT.md` 或现有 `AGENT-*.md`，保持短而密：

- 项目和文档版本；
- 真实术语、对象、状态、模块索引；
- 架构与关键链路摘要；
- 已选高价值主题及选择依据；
- 当前实现、未实现能力和不可声称事项；
- 个人贡献表达基线；
- 简历和项目介绍的唯一版本位置；
- `U` 类事实；
- 下次可直接使用的回顾提示词。

Agent 文档可以有意复述核心事实，但不能成为新的事实源。

## 三、可选内容模块

以下是内容能力，不是固定文件。可按项目合并、拆分、改名或删除。

### 项目全景

适用于业务边界、上下游、领域对象或整体架构本身有理解成本的项目。包含业务目标、角色、系统边界、模块关系、核心不变量和总体图。

### 关键链路与状态

适用于状态机、工作流、异步编排、复杂交互或失败补偿突出的项目。包含正常/异常时序、合法状态迁移、外部副作用、重试和人工处置。

### 高价值技术主题

每个主题围绕真实问题展开，而不是写组件百科。主题可能是：

- 事务、并发控制、数据建模或查询性能；
- 缓存、消息、任务调度、分布式一致性或容灾；
- JVM、语言特性、内存、线程或运行时性能；
- API、网络协议、网关、鉴权或安全；
- 前端状态管理、渲染性能、工程化或全栈边界；
- Agent、RAG、工具调用、上下文工程、评测、模型路由或成本延迟；
- 搜索、推荐、数据管道、索引或离线在线一致性；
- 云原生、发布、可观测性、测试策略或故障定位；
- 项目特有的算法、规则引擎、领域建模或第三方集成。

仅保留实际入选的主题。每个主题统一回答：

1. 场景和约束；
2. 仓库中的当前实现；
3. 为什么这样设计；
4. 替代方案与取舍；
5. 失败模式和适用边界；
6. 如何测试、观测或证明；
7. 面试官可能怎样连续追问；
8. 需求或规模变化后的演进。

### 个人贡献与面试表达

可以单独成文，也可以与追问题库合并：

- 面经调研范围和查询台账；
- Git 个人贡献事实表；
- 精简版与展开版项目介绍；
- 3～5 个证据卡片或 STAR 故事；
- 简历成稿；
- 按入选主题组织的连续追问；
- 面向不同岗位的表达差异；
- 不可声称事项和待确认事实。

## 四、文档结构示例

以下只说明适配方式，不是标准答案。

- `权限、数据正确性与工程质量.md`
- `面试表达与追问.md`

### Agent 应用项目

## 五、完成标准

让没有源码上下文的读者只凭文档回答：

1. 项目解决什么问题，怎样运行；
2. 本项目最值得讲的两到五个设计是什么，为什么是它们；
3. 这些设计在代码中如何落地，边界和替代方案是什么；
4. 当前目标岗位为什么会追问这些内容；
5. 个人实际负责什么，证据能证明到哪里；
6. 简历表述如何自然展开为连续追问；
7. 哪些事实未知，哪些内容只是未来演进。
